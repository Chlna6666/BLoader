# BLoader 0.2.19

## Runtime readiness without graphics hooks

BLoader no longer creates a dummy Win32 window, DXGI factory, D3D12 device, command queue, or dummy swapchain to discover `IDXGISwapChain::Present` for delayed Mod injection.

Delayed `hot-native` and `hot-inject` loading now uses a non-graphics runtime readiness state machine:

- Minecraft OEP must be released by the Pre-Main Gate.
- `process` readiness requires only OEP release.
- `window` readiness requires a visible Minecraft-process window with a usable client area.
- `stable-window` readiness requires the same visible window to remain available for 750 ms.
- Top-level and child windows are scanned so packaged/UWP CoreWindow-style hosts are supported without touching D3D/DXGI.
- The BLoader debug console HWND is explicitly excluded from readiness detection.
- `inject_delay_ms` is enforced relative to Minecraft OEP release.

### Manifest compatibility

A hot Mod may now specify:

```json
{
  "type": "hot-inject",
  "inject_ready": "stable-window",
  "inject_delay_ms": 5000
}
```

Supported `inject_ready` values are `process`, `window`, and `stable-window`.

Defaults:

- `hot-native`: `window`
- `hot-inject`: `stable-window`

`inject_min_frames` remains parseable for compatibility but is deprecated and ignored. BLoader emits a warning instead of installing a graphics/Present hook.

## UWP compatibility

The old render-readiness probe ran before Minecraft OEP and could initialize USER32/DXGI/D3D12 before older UWP Minecraft versions initialized their own application and graphics stack. 0.2.19 removes that startup-side graphics activity entirely.

The real D3D12 queue/export interfaces used by Mods are unchanged; only the readiness probe was replaced.

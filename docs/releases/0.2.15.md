# BLoader 0.2.15

## PreLoader-first bootstrap

This release changes the priority `type: "preload"` / `PreLoader.dll` path so the loader is initialized at the earliest safe point on BLoader's `bloader-bootstrap` thread.

### Fixed

- PreLoader is now the first third-party DLL loaded by `bloader-bootstrap`, immediately after the thread starts and the crash handlers are armed.
- PreLoader no longer waits for BLoader config loading, debug-console allocation, process-wide stdout/stderr capture, render/network hooks, or normal Mod loading.
- The priority PreLoader path no longer uses `native_stdio::capture_library_load`; BLoader therefore does not temporarily rebind process-global Win32/CRT stdout and stderr around PreLoader initialization.
- BLoader still avoids calling third-party `LoadLibraryW` directly from `DllMain`, preventing nested loading while the Windows loader lock is held.
- If PreLoader loads successfully, it retains ownership of the remaining preload chain and BLoader skips the legacy native preload pass.
- If PreLoader is missing or its `LoadLibraryW` call fails, BLoader retains the legacy preload fallback.

### Diagnostics

Early bootstrap markers now record:

- `dllmain.preloader.deferred target=bloader-bootstrap-first`
- `bootstrap.preloader.early.begin`
- selected PreLoader package/path
- bare `LoadLibraryW` begin state (`capture=process-crt-disabled`)
- early success/failure and elapsed time
- delegation or legacy-fallback state after the global logger becomes available

The early markers are written before the normal logger/console pipeline and remain available in the bootstrap/latest logs for diagnosing failures during PreLoader initialization.

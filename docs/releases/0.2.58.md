# BLoader 0.2.58

## Xbox / XUser 混合认证加固

本版本继续使用 0.2.57 引入的职责划分：

- **BMCBL**：仅向 Minecraft 进程交付目标账号的原始 XASU `UToken` 与公开用户元数据；MSA refresh token 不进入游戏进程。
- **Microsoft Gaming Runtime / xgameruntime.dll**：负责官方 Device/Title 上下文、最终 XSTS、Token cache/ForceRefresh 与 HTTP Proof-of-Possession Signature。
- **BLoader**：在官方 XSTS 请求签名前仅替换 `Properties.UserTokens`，保留官方 `DeviceToken`、`TitleToken`、RelyingParty 与签名上下文。

## 0.2.58 修复

1. 增加按 RelyingParty 记录的 UToken 重写 generation。Xbox Live、PlayFab、Minecraft Multiplayer、Realms 与 Licensing 分别建立自己的官方 XSTS 自定义用户缓存状态。
2. 某个 RelyingParty 第一次通过自定义会话请求 Token 时，BLoader 自动为原生 `XUserGetTokenAndSignature*` 增加 `ForceRefresh`，避免直接命中 backing Windows 用户已有的 XSTS cache。
3. 调用方本身指定 `ForceRefresh` 时，BLoader 要求本次请求重新观察到对应 RelyingParty 的 UToken 注入；如果官方 Runtime 未进入 XSTS 聚合链，则结果失败关闭。
4. 自定义 UToken 已过期或不足 30 秒有效期时，不再调用原生 Token provider，避免静默返回 backing 用户的 Authorization/Signature。
5. BCrypt 签名票据现在同时绑定原生 UToken 指纹与 RelyingParty；WinHTTP 发送阶段只有同时匹配时才允许提交修改后的 XSTS body。
6. 如果 BMCBL 选择的账号恰好就是当前 backing Windows 用户，仍会记录完整的签名/发送链，不会因为 UToken 内容相同而误判为“未注入”。

## 预期日志

首次访问一个 RelyingParty 时应出现：

```text
首次请求该 RelyingParty；强制官方 Runtime 刷新 XSTS 以建立自定义用户缓存
官方 XSTS 签名输入已绑定自定义 UToken
官方 XSTS UToken 签名票据已生成
官方 XSTS HTTP 请求已绑定自定义 UToken
```

如果官方 Runtime 在强制刷新后没有经过受保护的 D + T + U 聚合链，则 BLoader 返回失败而不是泄漏 backing 用户 Token：

```text
拒绝原生 XSTS 结果 | reason=custom-utoken-rewrite-not-observed | action=fail-closed
```

## 已知边界

- XSTS 聚合点仍属于 `xgameruntime.dll` 内部实现。当前实现通过 BCrypt 签名输入与 WinHTTP 请求体配对验证实际替换链；微软 Runtime 改变内部签名/传输实现时会失败关闭，需要根据日志适配新的内部路径。
- 启动时的 UToken 仍通过一次性进程专属管道交付。BMCBL 保存的 MSA refresh token 不会进入 Minecraft；超长游戏会话若跨越 UToken 本身的有效期，需要后续进程期 refresh 控制通道才能无缝更新原始 UToken。
